\section{Introduction}

An LLM agent reads from many places. It reads retrieved documents and the output of the tools it calls. It reads the descriptions of those tools, the files and skills it loads, and messages
from other agents. It also reads its own stored memory~\cite{chu-2026-systematic,ma-2025-safety}. All of this arrives in one context window, and the model treats it as one body of
text. The model has no reliable way to tell which part of that text is trustworthy and which part is not~\cite{greshake-2023-not}. Think of the context window as a pond fed by a fixed set of streams. Whatever
enters through any stream mixes into the same water, whether someone dumped it
in or it washed in on its own. So the first questions are how many streams
there are and how many kinds of damage the pollution can do.

Two research communities study what goes wrong when untrustworthy content gets
in, and they use different words for it. The security community studies content that an attacker placed there on purpose. It names attacks such as indirect prompt
injection~\cite{greshake-2023-not}, retrieval
poisoning~\cite{zou-2024-poisonedrag,zhong-2023-poisoning} and memory
backdoors~\cite{dash-2026-untrusted}, and it publishes defenses against
them~\cite{xiang-2024-certifiably,liu-2025-datasentinel,an-2025-ipiguard}.
Success means the attacker fails to achieve a goal.

The safety community studies content that became wrong without any
attacker. It names mechanisms such as lost-in-the-middle~\cite{liu-2023-lost} and
context rot~\cite{xia-2026-diagnosing}. It also names knowledge conflict, where a retrieved passage
disagrees with what the model already
learned~\cite{xie-2023-adaptive}. It publishes fixes for
them~\cite{huang-2025-parammute,bi-2025-parameters,yuan-2024-discerning}.
Success means accuracy goes up.

The two communities describe the same underlying failure: a passage the model
should not trust enters the context window and changes the output. Only the
provenance differs; the model sees tokens either way. The two communities
differ in more than vocabulary. They also differ in what counts as a
successful evaluation. The safety community measures a fix for the accidental
case on an average-case benchmark, because an accident does not adapt to the fix. The security community measures a defense for the
adversarial case against the worst case, because an attacker does adapt. Those are not two styles
of the same test. A method can pass the first test convincingly and fail the second one
completely. Because each community evaluates against its own convention, a
method is rarely tested against the other's.

So the field publishes, adopts and cites methods that are rarely evaluated
against the other community's test. We test that claim by
reading both literatures under one taxonomy and recovering every experiment
either side has run. Almost none of those experiments cross
between the communities. We then run the missing ones to answer the
following research questions.

\paragraph{Research questions.}
\begin{description}
\item[RQ1] \textbf{Do the two communities duplicate each other's work?} We read
  \NCorpus{} papers from both sides under one scheme, compare where each
  community's fixes intervene, and recover every (fix, mechanism) pair
  the \NAnalysed{} papers that name a technique report
  (Sections~\ref{sec:literatures}, \ref{sec:parallel}).
\item[RQ2] \textbf{Does a fix built for one literature's problem
  survive the other's?} We execute the pairs the literature skipped, from the
  authors' released code and weights
  (Sections~\ref{sec:campaign}, \ref{sec:results}).
\item[RQ3] \textbf{Is failure a property of individual methods or of a
  design choice they share?} We build a planted passage that separates the
  explanations rather than maximizes damage
  (Section~\ref{sec:distractor}).
\item[RQ4] \textbf{Do the measurements the field leaves out change the
  result?} We re-read every result against a score almost no paper
  reports: what the same model scores with no document at all. We also check
  the results on a second base model and on a second implementation of the
  one design that held (Section~\ref{sec:controls}).
\item[RQ5] \textbf{Does that explanation survive an adaptive attacker?} We
  build two optimizers against the one method that resisted
  (Section~\ref{sec:adaptive}).
\end{description}

\paragraph{What we find.} Methods from each community fail on the other
community's problem, and they fail for opposite reasons. The safety fixes
decide how much to trust the retrieved document compared with what the model
already knows. That choice cannot tell an honest document from a planted
one. Against an attacker, these fixes either hand answers to the attacker or
send them back to the model's memory. They never move them to the true
document. The security defenses that take a vote across passages work while
most passages are correct. That is true when an attacker can plant only a
few passages. It is not true when a fact goes out of date, because many
retrieved passages can then be wrong at the same time. With five copies of
an out-of-date page among ten passages, the vote gives the outdated answer
more often than no defense does. The defenses that look for injected
instructions find none in an honest mistake, and change nothing. Each design
relies on an assumption that is true for the problem it was built for and
false for the other one.

Both literatures have been systematized before: the security side
repeatedly~\cite{dehghantanha-2026-sok,chu-2026-systematic,jiang-2026-sok},
and the safety side on its own terms as a problem of knowledge
conflict~\cite{xu-2024-knowledge}. None of it runs the experiment. A
survey of one literature has only that literature's methods in hand, and the
test we need takes a fix from one side and a mechanism from the other. So we
read both, found the pairs no paper reports, and ran them from the authors'
released code and weights. To our knowledge this is the first evaluation
in which published fixes from one of these communities meet published
mechanisms from the other.

\paragraph{Scope.}
Three limits bound what follows. Each experiment runs on one dataset, and we
plant poisoned passages into the context rather than attack the retriever, so
the numbers describe what a model does with bad text once it has it. Each fix runs
on one base model of 7 to 14 billion parameters, chosen by what its authors
released, and only RobustRAG also runs on a second. Almost every attack we run was not designed against the fix it
meets. If a fix loses to such an attack, it would also lose to a stronger
one. If it holds, that tells us little.

\paragraph{Contributions.}
\begin{itemize}
\item \textbf{A map of how the two communities share one problem.} We place
  every mechanism and fix from both literatures in one taxonomy and along one
  picture of the agent's pipeline. It shows where each community works:
  security fixes guard where text enters, and safety fixes improve how
  the model reasons about text already inside. It also shows that a system
  built only from one community's methods is unprotected at the stage the
  other community covers
  (RQ1; Sections~\ref{sec:literatures}, \ref{sec:parallel}).

\item \textbf{The first evaluation across the two communities.} We run
  \NCampaignPairs{} pairs that put a fix from one community against a
  mechanism from the other, each from its authors' released code and weights,
  and report how each fix holds up outside the setting it was built for. For
  the defenses that vote, we read their own traces to show which passages
  decided the answer, and we test whether attribution finds the passage
  behind an honest failure
  (RQ2; Sections~\ref{sec:campaign}, \ref{sec:results}).

\item \textbf{A test that tells copying from remembering.} We plant a passage
  asserting an answer that is neither true nor the model's own, so every
  output shows whether the model read the real document, recalled from
  memory or copied the attacker. We use it to ask whether the failures belong
  to individual methods or to a choice they share (RQ3;
  Section~\ref{sec:distractor}).

\item \textbf{The measurements the field leaves out.} We add a no-document
  score, a second base model and a second implementation to the results, and
  show which conclusions depend on them (RQ4; Section~\ref{sec:controls}).

\item \textbf{A test of the one fix that held, against an attacker who
  knows it.} We build two
  attacks against that fix's own rule, one by rephrasing and one by
  gradient search, and measure how much of its protection survives an
  attacker who knows its rule (RQ5; Section~\ref{sec:adaptive}).

\item \textbf{What a fix covering both regimes cannot assume.} From the two
  directions we derive three assumptions such a fix must do without: that the
  document is honest, that wrong passages are few, and that a wrong passage
  contains an instruction (Section~\ref{sec:neither}). We have also started an
  experiment that stacks a fix acting where text enters in front of one
  acting where the model reasons. It is not finished, and we claim no result
  from it (Section~\ref{sec:discussion}).

\item \textbf{A runnable artifact.} Every fix and every published attack
  executes from its authors' released code at a pinned commit, and we checked that the code is unchanged. We
  release our test code, the planted passages and the full list of coded
  papers.
\end{itemize}

\paragraph{How the paper reads.} Section~\ref{sec:background} defines the
terms and the threat model. Section~\ref{sec:literatures} answers RQ1 and
ends at the region the literature has barely tested. Section~\ref{sec:experiments} describes
the platform, Section~\ref{sec:setup} the setup and the experiments we ran on
it, and Section~\ref{sec:results} what they show, grouped under RQ2 to RQ5.
Section~\ref{sec:discussion} turns the
results into conventions for evaluation, into advice for deployment, and
into the design rule a fix covering both regimes would have to follow.
Section~\ref{sec:threats} states the limits and what is not finished.
